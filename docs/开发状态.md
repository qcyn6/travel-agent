# MVP 开发状态

本文件记录 `个性化旅游规划系统_MVP方案_V2.md` 与
`个性化旅游规划系统_MVP详细开发步骤_V2.md` 的实际实现状态。

## 前端对话式演示

- 已增加 Vue 3 + TypeScript + Vite 前端。
- 已实现自然对话、实时需求卡、可编辑确认单、SSE 规划进度和最终逐日行程页面。
- 已增加 MySQL `conversations`、`conversation_messages` 表，支持当前匿名会话内的多轮记忆。
- 同一标签页使用 `sessionStorage` 恢复当前会话和已生成方案；历史侧边栏支持多个匿名会话切换。
- 登录、用户隔离、天气、地图和预算计算不属于当前阶段。

## 最终版本增量

- 已在 Git 标签 `mvp-v1.0` 冻结 MVP。
- 已完成结构化行程数据契约：出发日期、交通方式、POI ID 和景点坐标进入规划结果。
- 已完成高德 Route Tool 与 TravelPlan 集成，支持步行、公交和驾车路线。
- 高德路线失败时降级为 Haversine 估算；缺少坐标时明确标记为不可用。
- 最终方案页面已展示相邻景点的交通方式、距离、时间和估算标记。
- 已完成和风天气逐日预报接入，使用行程日期和景点坐标查询并在最终方案展示。
- 未提供日期时天气状态为 `skipped`；超出十日范围或服务异常时为 `unavailable`，不会阻断规划。
- 已增加 MySQL `attraction_facts` 景点事实表，开放时间与游玩时长不再混入检索摘要。
- 开放时间保留结构化时段、原文、适用条件、来源、可信度与核验时间；未知时明确降级且不阻断规划。
- 建议游玩时长优先从已核验网页提取，来源没有明确依据时按景点类别给出低可信度估算。
- 已增加确定性 Schedule Builder，以 09:00 为默认起点，组合景点游览、相邻路线、90 分钟用餐和 60 分钟缓冲。
- 每个景点现在带有预计开始/结束时间；每日时间表明确标记为完整、含估算或数据不完整。
- 已实现规则型 Evaluator：检查每日密度、单段/全天交通、降雨与户外安排、开放时间和兴趣覆盖。
- `high` 问题会设置 `replan_required=true`；开放时间为 `unknown` 时不制造硬冲突，偏好不足只作为软提示。
- 已实现 DeepSeek 局部 Replanner，只能从当前城市 RAG 候选 POI 中调整问题日期；模型不可用时保守删减。
- Replanner 后仅重新获取受影响日期的路线、景点事实和时间表，其他日期保持不变。
- 已使用 LangGraph 建立 `Evaluator → Replanner → Evaluator` 条件反馈环，最多自动调整 2 次并明确返回是否达到上限。
- 已实现可选 Redis Cache-Aside，缓存高德 POI、路线、和风天气和 Tavily 来源搜索结果。
- Redis 未配置或连接失败时自动按缓存未命中处理，不影响外部 API 调用与 MySQL 主数据；TTL 均可通过环境变量配置。
- Windows 本地开发可通过 `REDIS_WSL_DISTRO` 自动启动 WSL 隐藏保活进程，避免 Redis 随空闲 WSL 实例停止。
- 最终方案页已增强为可执行 Day Card：展示起止时间、游览/交通/用餐/缓冲汇总、事实来源和估算标记。
- 前端以通过、提示、待核验三种语义展示 Evaluator 结果，不展示缺乏解释性的模型分数。
- 已统一收集路线估算/缺失、天气跳过/不可用、开放时间未知、时间表不完整和重规划达到上限等降级说明。
- 外部服务降级会写入后端 warning 日志，并在最终方案“数据说明”中向用户解释，不泄露 API Key 或连接信息。
- 已增加 MySQL `travel_plans` 表，按当前会话保存需求、完整方案、评估结果和递增版本号。
- 新增 `GET /api/v1/conversations/{conversation_id}/plans`，为后续登录后的历史方案列表保留稳定接口。
- 已增加 MySQL `planning_jobs` 与 `planning_events` 表，持久化规划任务状态和进度事件；支持重复提交复用任务、刷新后回放进度、断线后恢复观察。
- 规划 worker 通过 `worker_id + heartbeat_at` 持有数据库租约；只有租约持有者可以写入进度和最终结果，服务重启后其他进程会在租约超时后接管未完成任务。
- 默认开发环境仍由进程内任务注册表触发；生产环境可启用 Redis Streams 外部队列并单独运行 `scripts/run_planning_worker.py`，worker 会扫描补发遗漏的 queued 任务。
- 已增加 Prometheus 文本格式的 `/metrics`，记录 HTTP、规划任务、SSE、租约、队列和外部服务调用指标。
- 规划失败、队列不可用、worker 未处理异常和队列确认失败会写入结构化告警日志；配置 `ALERT_WEBHOOK_URL` 后可转发到运维 Webhook。
- 已提供 `scripts/run_acceptance.py`，可重复验证杭州 1 天、杭州 3 天和云南 7 天三条真实端到端工作流。
- 已提供 `scripts/run_e2e_acceptance.py`，可验证重复提交复用任务、SSE 断线续传、事件序列完整性、租约接管、Embedding 降级和单份方案落库。
- 已将目的地目录扩展为全国 34 个省级行政区、372 个城市/地区入口；保留单城市与同省 2～3 城市流程，跨省多城市继续拦截。
- 已建立 24 组固定 A/B 实验集，对比无工具 LLM 直接生成与完整规划系统。
- 实验评分与系统 Evaluator 解耦，独立计算景点有效率、兴趣覆盖率、时间可行性、路线合理性和外部约束满足率。
- 当前自动化测试为后端 135 项、前端 7 项，前端生产构建通过；真实验收结果见 `docs/最终版本验收报告.md`。

## 数据边界

- MySQL 保存全国省级行政区、目录中的城市/地区、查询过的高德 POI 和已经生成的景点知识。
- Chroma 只按需保存已完成知识的向量，不预构建全国景点库。
- Redis 已作为最终版本增量接入，只缓存有时效性的外部 API 结果，不作为景点主存储。
- `failed` 知识不会被普通规划请求反复重试；可通过单景点强制刷新接口显式重试。
- 当前仍不实现跨省多城市、复杂预算和城市间精确交通优化；Evaluator、Replanner、天气和路线能力已按最终版本实现。
