## 3. 开题报告定义的目标核心流程

开题报告中的规划模式可以归纳为以下确定性主链：

```text
用户自然语言输入
    ↓
LLM 解析 + 本地规则补全 TravelRequirement
    ↓
Destination Planner 确定省份、城市组合和停留天数
    ↓
MySQL attractions 读取目标城市候选
    ↓
interests 与 tags 做硬筛选
    ↓
Chroma Semantic + BM25 Keyword
    ↓
PreferenceScore = 0.7 × SemanticScore + 0.3 × KeywordScore
    ↓
从当前规划位置计算 Haversine 距离与 DistanceScore
    ↓
Priority = 0.7 × PreferenceScore + 0.3 × DistanceScore
    ↓
按 Priority 逐个尝试候选
    ↓
高德 MCP Route 获取真实路线和交通时间
    ↓
在每日时间窗口内验证游览、交通、用餐和缓冲是否可容纳
    ↓
加入可行景点并更新当前位置、当前时间、剩余候选分数
    ↓
天气补充 + Rule-based Evaluator
    ↓
保存 Structured TravelPlan 并由前端展示
```

这里有三个不可替代的课题核心：

1. 大语言模型负责理解需求，不负责直接决定最终景点顺序。
2. 景点选择不是一次性排序，而是当前位置和时间不断变化后的动态决策。
3. 路线查询不是方案生成后的装饰，而是候选景点能否加入行程的可行性条件。

## 4. 当前仓库已经完成的能力

### 4.1 双模式前后端骨架

当前已经存在普通模式与规划模式两套独立会话、接口和前端历史入口：

- 普通会话：`backend/api/general_conversations.py`、`backend/conversation/general_service.py`

普通消息不会直接写入规划需求，规划模式也会拒绝越界的普通聊天。这一部分与开题报告的“双模式隔离”目标基本一致。

### 4.2 需求解析与多轮收集

`TravelRequirement` 已覆盖：

- 省份和城市；
- 旅行天数；
- 兴趣标签；
- 自由文本体验偏好；
- 单城市或同省多城市范围；
- 出发日期；
- 每日开始和结束时间；

当前具备 LLM 结构化解析失败后的本地解析降级、省市标准化、相对日期解析、出发日期限制、时间窗口校验和需求确认流程。

### 4.3 目的地规划

当前支持：

- 1～3 天单城市；
- 4～7 天强制同省多城市；
- 最多 3 个城市；
- 每个城市至少 1 天；
- 指定城市、指定省份后推荐城市、未指定省份时按兴趣推荐；
- 跨省多城市拦截。

目的地推荐目前主要按省市标签匹配和稳定顺序决策，能够满足 MVP，但还不是论文重点，不需要在动态排程完成前继续复杂化。

### 4.4 景点硬筛选和偏好混合检索

- `preference_text` 用于语义检索和 BM25 关键词检索；
- 语义服务不可用时可以保留本地结果继续；
- `PreferenceScore = 0.7 × semantic + 0.3 × keyword`；
- 向量检索按城市过滤；
- 最终候选包含 `preference_score`、`keyword_score` 等检索信息。

这一部分已接近报告定义，后续重点不是重写检索，而是确保检索分数不会在进入规划器时丢失。

### 4.5 外部路线、天气与降级

## 5. 当前实现与开题报告的关键差距

### 5.1 P0：动态 Priority 排程与路线约束已接入

阶段 2 完成了不依赖外部服务的动态排程核心，阶段 3 又把单段路线查询和严格时间校验接入了正式工作流。

当前 `backend/planner/dynamic_scheduler.py` 负责：

- 第一天的第一站按 `PreferenceScore` 选择；
- 后续候选按 Haversine 距离、`DistanceScore` 和 `Priority = 0.7 × PreferenceScore + 0.3 × DistanceScore` 动态排序；
- 每加入一个景点后重新计算剩余候选；
- 先做游玩时长粗筛，再对优先候选查询路线，结合游玩时长、路线、用餐和缓冲做严格时间校验，并生成 `CandidateDecision` 轨迹；
- 多日计划优先保持景点不重复，候选不足时明确记录复用原因。

`CityPlanningService` 现在由确定性排程器拥有最终景点列表，DeepSeek 只可补充每日自然语言说明，不能覆盖景点选择和顺序。路线结果在候选入选时生成，并直接复用到最终时间表。

### 5.2 P0：PreferenceScore 在规划边界被丢失

`backend/rag/hybrid.py` 已经生成 `HybridSearchResult.preference_score`。阶段 1 已新增内部 `PlanningCandidate` 模型，由 `backend/planner/service.py` 把 `semantic_score`、`keyword_score`、`preference_score` 和 `tag_match_count` 一并传入城市规划器，分数不再在规划边界丢失。

阶段 2 已使用这些分数计算动态 `DistanceScore` 和 `Priority`；阶段 3 已在每一步进行路线可行性验证。

### 5.3 P0：路线验证已移入选点循环

当前正式工作流顺序是：

```text
候选检索
  → 高德详情补齐（可选）
  → 动态排程器按偏好、距离和本地时长粗筛
  → 对候选逐个查询路线并做严格时间校验
  → 可行候选入选并更新当前位置
  → 复用已验证路线生成时间表
  → 天气与评估
```

报告要求的顺序是：

```text
候选排序
  → 对优先候选查询路线
  → 判断路线 + 游览 + 用餐 + 缓冲是否可放入当天
  → 可行才加入
  → 更新当前位置和时间后继续选下一个
```

高德失败时沿用现有 Haversine 估算降级；缺坐标或没有路线耗时的候选会被记录为不可用，不会伪装成真实路线。

### 5.4 P0：严格时间表已成为选点约束

`DynamicCityScheduler.plan_with_routes` 会在路线和时间校验失败后继续尝试同轮其他候选。`ScheduleBuilder.build_day_exact` 会要求所有已选景点和相邻路线完整可行，不再通过删除景点来制造合法时间表。

旧的 `build_day` 仍保留给历史调用和兼容读取；正式路线感知工作流使用严格的 `build_day_exact`。

### 5.5 P0：短行程的城市范围规则已统一

开题报告定义的“1～3 天单城市深度游，4～7 天同省多城市”已经收口到同一套边界函数 `scope_day_boundary_error`。需求模型、自然语言解析、目的地解析、目的地规划器、会话提示和前端建议均复用或遵循这套规则：

- 1～3 天只能生成单城市方案；
- 4～7 天必须生成同省 2～3 城市方案；
- 解析到短行程多城市时直接提示增加天数，不进入规划工作流；
- 历史会话读取时会把旧的冲突范围重新打开为待确认，不破坏已有会话；
- 多城市天数建议在前端和会话层只展示 4～7 天。

### 5.6 P1：普通模式工具路由已完成

开题报告要求普通模式按单一意图路由：

- 旅游知识 → Markdown RAG；
- 路线问题 → 高德 MCP；
- 天气问题 → 和风天气；
- 明确规划意图 → 提示切换规划模式。

当前普通模式通过确定性规则完成单一意图分类和参数抽取：路线查询复用高德 MCP 与既有估算降级，天气查询复用和风天气，参数不完整时只追问缺失项。规划意图仍只提示切换规划模式，普通模式不会创建规划任务或写入规划需求。

## 6. 目标核心架构

### 6.1 目标职责划分

| 模块 | 目标职责 | 是否使用 LLM |
| --- | --- | --- |
| Requirement Parser | 从自然语言形成结构化需求，本地规则补全与校验 | 是，可降级 |
| Destination Planner | 选择省份、城市和停留天数 | 否，确定性规则 |
| Candidate Retriever | 标签硬筛选、Chroma、BM25、PreferenceScore | 否 |
| Dynamic Scheduler | DistanceScore、Priority、时间窗口、候选循环 | 否 |
| Route Feasibility | 对优先候选查询真实路线并判断可行性 | 否，调用高德 |
| Weather Enrichment | 最终逐日天气补充 | 否，调用和风 |
| Evaluator | 规则检查和结构化问题 | 否 |
| Response Narrator | 将结构化结果转成自然语言说明，可选 | 可选 |

核心原则：LLM 可以解释，不能覆盖确定性算法的结果；LLM 不可用时，核心行程仍应生成。

### 6.2 建议的数据模型

新增内部候选模型，不直接污染数据库表：

```python
class PlanningCandidate:
    poi_id: str
    name: str
    city: str
    tags: list[str]
    longitude: float | None
    latitude: float | None
    visit_duration_minutes: int
    preference_score: float
    semantic_score: float | None
    keyword_score: float
```

每次动态决策生成内部轨迹：

```python
class CandidateDecision:
    poi_id: str
    day: int
    preference_score: float
    distance_m: float | None
    distance_score: float
    priority_score: float
    feasible: bool
    selected: bool
    rejected_reason: str | None
```

阶段 2～3 的决策轨迹先用于日志、测试和实验，不直接暴露给最终用户。路线来源和耗时保存在现有 `RouteSegment` 中，并与选点结果按天关联，方便论文解释和问题排查。

### 6.3 动态排程算法

建议的确定性伪代码：

```text
输入：城市停留天数、候选景点、每日时间窗口、用餐和缓冲配置

unused = 所有通过标签硬筛选的候选

for 每一天:
    current_time = 每日开始时间
    current_location = None

    while unused 非空:
        if current_location is None:
            第一站按 PreferenceScore 选择
        else:
            计算 current_location 到所有候选的 Haversine 距离
            Dmax = 当前候选最大距离
            DistanceScore = 1 - distance / Dmax
            Priority = 0.7 * PreferenceScore + 0.3 * DistanceScore

        按 Priority 从高到低尝试候选:
            先用访问时长 + 基础缓冲做本地粗筛
            第一站无需路线；其余候选调用高德 Route
            Route 失败且坐标可用时生成带标记的 Haversine 估算
            计算交通 + 游览 + 用餐 + 缓冲后的结束时间

            if 可在当天结束时间前完成:
                加入当天
                更新 current_location 和 current_time
                从 unused 移除
                break，重新计算剩余候选 Priority

        如果所有候选均不可行:
            结束当天

输出：逐日景点、已验证路线、时间线、未选原因、决策轨迹
```

### 6.4 第一站和缺失坐标的确定规则

开题报告没有明确“每天第一站从哪里出发”。第一版建议采用最简单、可复现的规则：

- 每天第一站只按 `PreferenceScore` 选择；
- 不假设用户酒店或车站位置；
- 第二站开始才使用当前位置计算 `DistanceScore`；
- 未来如新增住宿位置，再把酒店坐标作为每日起点。

缺失坐标处理：

- 有明确兴趣匹配但缺少坐标的景点仍可作为第一站候选；
- 缺坐标景点不能参与后续距离优先度和路线验证时，应降低优先级或跳过，并记录原因；
- 不允许用城市中心点冒充景点坐标。

### 6.5 调用量控制

动态排程会增加路线调用次数，必须控制成本和延迟：

- 检索阶段每城市先取 20～30 个候选，不把全国数据送入规划器；
- 本地时长粗筛先排除明显放不下的候选；
- 每一轮只对 Priority 前 3～5 名调用路线；
- 继续使用 Redis 路线缓存；
- 同一对景点和模式命中缓存时不重复请求；
- 记录每次计划的路线调用次数、缓存命中率和总耗时；
- 如果全部真实路线失败，允许带明确标记的估算结果继续，不得伪装成真实路线。

| Iteration 1 核心算法 | 5 天 | 分数契约、动态 Priority 排程、单元测试 | 不依赖 LLM 生成景点顺序 |
| Iteration 2 流程闭环 | 4 天 | 路线可行性、时间窗口、工作流重组、持久化 | 三个代表案例端到端成功 |
| Iteration 3 双模式完善 | 3 天 | 评估统一、前端解释、普通模式路线/天气 | 双模式功能与报告一致 |
| Iteration 4 实验与交付 | 4 天 | A/B 与消融实验、文档、演示脚本 | 自动测试全绿且实验可复现 |

总计约 16 个工作日。若时间紧张，应按以下顺序裁剪：

1. 必须完成：Iteration 1 和 2。
2. 优先完成：Iteration 3 中的评估统一，普通模式路线/天气可稍后。
3. 论文必须完成：Iteration 4 中至少一个 baseline 对比和一个距离因素消融实验。
4. 可延期：全国景点数据完善、复杂性能优化、更多城市实验和 UI 美化。

## 9. 核心完成定义

只有同时满足以下条件，才可以把“核心流程完成”写进 README 或论文：

- 用户能通过多轮自然语言形成完整 TravelRequirement。
- 1～3 天单城市和 4～7 天同省多城市边界稳定。
- 景点只来自本地数据库候选，不由 LLM 编造。
- interests 与 tags 的硬筛选真实生效。
- Semantic、Keyword 和 PreferenceScore 可追溯。
- 第二站开始使用当前位置计算 DistanceScore。
- 每加入一个景点后重新计算 Priority。
- 路线和时间窗口在景点加入前参与判断。
- 不可行候选会被跳过并尝试下一候选。
- 最终行程不靠事后删除景点才能满足时间窗口。
- 路线、天气和估算结果有清晰来源标记。
- Evaluator 输出时间、路线、兴趣和数据可信度问题。
- 方案能保存、恢复并在前端完整展示。
- LLM、Embedding、高德或天气服务单项失败时有定义明确的行为。
- 后端和前端自动化测试全部通过。
- 至少三条固定端到端案例通过。
- 至少完成一次 LLM Baseline 对比和一次权重/距离消融实验。

## 10. 测试规划

### 10.1 单元测试

重点新增：

- 分数归一化和公式；
- 动态顺序变化；
- 距离与坐标异常；
- 路线可行性和降级；
- 用餐、缓冲和边界时间；
- 候选替换而不是截断；
- 多日去重；
- 评估指标。

### 10.2 集成测试

重点覆盖：

- Retrieval → PlanningCandidate；
- Dynamic Scheduler → Route Service；
- Scheduler → TravelPlan；
- Workflow → 持久化任务与事件；
- 方案保存后重新读取；
- 普通模式意图到工具调用。

### 10.3 API 测试

重点覆盖：

- 需求确认后生成计划；
- 重复提交复用任务；
- SSE 断线恢复；
- 目的地选择后继续同一任务；
- 规划失败后能够修改需求并重试；
- 普通模式不能越权生成计划。

### 10.4 前端测试

重点覆盖：

- 规划进度新步骤；
- 真实/估算/不可用路线显示；
- 推荐理由；
- 结构化评估；
- 历史方案恢复；
- API 错误和重试。

### 10.5 真实服务验收

真实服务验收不应替代自动化测试。建议按以下层次运行：

1. 全部外部服务使用 Fake：快速、稳定、每次提交执行。
2. Embedding + Chroma 真实服务：确认向量维度、城市过滤和索引一致性。
3. 高德 + 和风真实服务：少量固定城市冒烟。
4. 全国矩阵：核心流程稳定后再运行，不作为日常开发门槛。

## 11. 风险与控制措施

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| 当前工作区改动过多 | 难以回退和定位回归 | 阶段 0 建立用户确认的基线，后续小步提交 |
| 动态排程增加高德调用 | 延迟和失败率上升 | 本地粗筛、Top-N 尝试、Redis 缓存、调用指标 |
| 坐标仍有不准确数据 | DistanceScore 和路线错误 | 代表城市先验收；缺坐标降级而不是伪造 |
| PreferenceScore 被归一化方式影响 | 实验结论不稳定 | 固定公式、保存原始分数、用消融实验比较 |
| LLM 输出波动 | 需求解析不稳定 | 本地规则合并；核心调度完全确定性 |
| 外部天气预报窗口有限 | 远期计划无法获得天气 | 标记 unavailable，不影响主计划生成 |
| 文档继续超前于代码 | 答辩时描述与演示冲突 | 每个里程碑结束后按代码事实更新文档 |
| 测试依赖当前日期 | 随日期自动失败 | 所有日期测试注入 reference_date |
| 旧方案模型兼容 | 历史方案读取失败 | Pydantic 迁移兼容、算法版本字段、回归样本 |

## 13. 最终建议

当前项目最值得保留的是完整的工程外壳和可靠性能力，阶段 2～3 已完成城市内部景点选择与路线约束的核心替换。下一步应沿用现有对话、检索、路线、天气、任务和前端模块，继续完善评估、解释和实验：

```text
旧：候选 → LLM/轮询分天 → 路线 → 截断

新：候选与 PreferenceScore
      → 动态 DistanceScore/Priority
      → 路线与时间可行性
      → 确定性逐步选点
      → 天气、评估与前端解释
```

核心规划闭环和双模式工具路由已经具备，下一阶段重点是完成固定系统验收、baseline 对比、距离因素消融与论文结果整理。数据库质量优化仍可在此基础上，以不改变算法接口的方式继续推进。
