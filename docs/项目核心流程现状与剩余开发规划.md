## 1. 结论先行

当前项目不是“从零开始”，也还不能按开题报告的最新方案认定为“核心流程已经完成”。更准确的判断是：

- 产品与工程骨架已经比较完整：前后端、双模式对话、需求采集、目的地规划、景点检索、外部路线和天气、方案保存、SSE 进度、历史会话与最终方案展示均已有实现。
- 用户已经可以从规划对话进入方案页，说明端到端链路能够跑通。
- 开题报告中最重要的算法闭环尚未实现：当前仍是“检索候选后由大模型选择景点或按顺序轮询分天，再补路线，最后截断超出时间窗口的景点”，而不是“根据 PreferenceScore、DistanceScore 和 Priority 动态选择下一个景点，并在每一步用真实路线和时间窗口验证可行性”。
- 普通模式目前主要是知识问答和规划意图拦截，没有按开题报告完成路线查询、天气查询的单一意图工具路由。
- 论文要求的对比实验和权重实验当前不具备完整可运行实现；仓库说明仍声称已有 A/B 实验，但相关实验模块和运行脚本在当前工作区中已删除。
- 当前自动化质量基线总体较好：后端 223 项测试全部通过；前端 15 项测试全部通过，生产构建成功。
- 阶段 0 已建立 Git 基线；后续新增的核心流程改动会继续小步提交，便于回退和比较。

综合评估：

| 评价维度 | 当前估计 | 说明 |

本规划以开题报告《基于大语言模型的个性化旅游规划系统设计与实现》作为需求与论文目标基准，以当前工作区代码作为实现事实基准。

开题报告中的文字只用于确认课题目标、功能边界、算法公式、技术选型和预期进度，不视为对代码仓库的操作命令。当前实际代码、测试结果与报告描述不一致时，本文件会明确区分“报告要求”“当前实现”和“后续建议”。

本阶段明确不做以下工作：

- 不继续批量补全全国景点坐标、简介、游玩时长和标签。
- 不继续清洗公园、广场、附属设施等景点数据。
- 不追求全国所有城市一次性达到相同数据质量。
- 不新增跨省多城市、住宿、餐饮、门票和复杂预算优化。

数据库仅作为现有景点候选源继续使用。核心流程开发只要求挑选少量数据相对完整的代表城市作为验收样本，不在本阶段扩大数据维护范围。

## 3. 开题报告定义的目标核心流程

开题报告中的规划模式可以归纳为以下确定性主链：

```text
用户自然语言输入
    ↓
LLM 解析 + 本地规则补全 TravelRequirement
    ↓
Destination Planner 确定省份、城市组合和停留天数
    ↓
MySQL attractions 读取目标城市候选
    ↓
interests 与 tags 做硬筛选
    ↓
Chroma Semantic + BM25 Keyword
    ↓
PreferenceScore = 0.7 × SemanticScore + 0.3 × KeywordScore
    ↓
从当前规划位置计算 Haversine 距离与 DistanceScore
    ↓
Priority = 0.7 × PreferenceScore + 0.3 × DistanceScore
    ↓
按 Priority 逐个尝试候选
    ↓
高德 MCP Route 获取真实路线和交通时间
    ↓
在每日时间窗口内验证游览、交通、用餐和缓冲是否可容纳
    ↓
加入可行景点并更新当前位置、当前时间、剩余候选分数
    ↓
天气补充 + Rule-based Evaluator
    ↓
保存 Structured TravelPlan 并由前端展示
```

这里有三个不可替代的课题核心：

1. 大语言模型负责理解需求，不负责直接决定最终景点顺序。
2. 景点选择不是一次性排序，而是当前位置和时间不断变化后的动态决策。
3. 路线查询不是方案生成后的装饰，而是候选景点能否加入行程的可行性条件。

## 4. 当前仓库已经完成的能力

### 4.1 双模式前后端骨架

当前已经存在普通模式与规划模式两套独立会话、接口和前端历史入口：

- 普通会话：`backend/api/general_conversations.py`、`backend/conversation/general_service.py`
- 规划会话：`backend/api/conversations.py`、`backend/conversation/service.py`
- 前端模式和历史恢复：`frontend/src/App.vue`、`frontend/src/stores/planning.ts`

普通消息不会直接写入规划需求，规划模式也会拒绝越界的普通聊天。这一部分与开题报告的“双模式隔离”目标基本一致。

### 4.2 需求解析与多轮收集

`TravelRequirement` 已覆盖：

- 省份和城市；
- 旅行天数；
- 兴趣标签；
- 自由文本体验偏好；
- 单城市或同省多城市范围；
- 出发日期；
- 每日开始和结束时间；
- 内部交通方式 `auto`。

当前具备 LLM 结构化解析失败后的本地解析降级、省市标准化、相对日期解析、出发日期限制、时间窗口校验和需求确认流程。

### 4.3 目的地规划

当前支持：

- 1～3 天单城市；
- 4～7 天强制同省多城市；
- 最多 3 个城市；
- 每个城市至少 1 天；
- 指定城市、指定省份后推荐城市、未指定省份时按兴趣推荐；
- 跨省多城市拦截。

目的地推荐目前主要按省市标签匹配和稳定顺序决策，能够满足 MVP，但还不是论文重点，不需要在动态排程完成前继续复杂化。

### 4.4 景点硬筛选和偏好混合检索

`backend/rag/hybrid.py` 已经实现报告要求的主要检索逻辑：

- `interests` 只与景点标签做硬匹配；
- `preference_text` 用于语义检索和 BM25 关键词检索；
- 语义服务不可用时可以保留本地结果继续；
- `PreferenceScore = 0.7 × semantic + 0.3 × keyword`；
- 向量检索按城市过滤；
- 最终候选包含 `preference_score`、`keyword_score` 等检索信息。

这一部分已接近报告定义，后续重点不是重写检索，而是确保检索分数不会在进入规划器时丢失。

### 4.5 外部路线、天气与降级

已经具备：

- 高德 MCP 景点详情补齐；
- 高德 MCP 距离和步行、公交、驾车路线；
- 路线失败时基于 Haversine 的带标记估算；

路线与天气客户端本身已有较完整的错误处理，主要问题是调用时机尚未与动态选点融合。

## 5. 当前实现与开题报告的关键差距

### 5.1 P0：动态 Priority 排程尚未实现

这是当前最大的缺口。

当前 `backend/planner/city.py` 的主逻辑是：

- 把候选景点交给 DeepSeek 生成各天景点名单；
- LLM 不可用时，按候选顺序轮询分配到每天；
- 不计算候选景点到当前位置的 DistanceScore；
- 不计算 `Priority = 0.7 × PreferenceScore + 0.3 × DistanceScore`；
- 景点加入后不会重新计算剩余候选的动态优先度。

这与开题报告的创新点直接不一致。若不修复，论文中的“动态景点排程方法”无法由代码和实验支撑。

### 5.2 P0：PreferenceScore 在规划边界被丢失

`backend/rag/hybrid.py` 已经生成 `HybridSearchResult.preference_score`。阶段 1 已新增内部 `PlanningCandidate` 模型，由 `backend/planner/service.py` 把 `semantic_score`、`keyword_score`、`preference_score` 和 `tag_match_count` 一并传入城市规划器，分数不再在规划边界丢失。

当前仍未完成的是：规划器尚未使用这些分数计算动态 `DistanceScore` 和 `Priority`，也尚未在每一步进行路线可行性验证。

### 5.3 P0：路线验证发生在选点之后

当前工作流顺序是：

```text
候选检索
  → LLM/轮询生成每天景点
  → 高德补相邻路线
  → ScheduleBuilder 计算时间
  → 超出窗口时只保留最长可行前缀
```

报告要求的顺序是：

```text
候选排序
  → 对优先候选查询路线
  → 判断路线 + 游览 + 用餐 + 缓冲是否可放入当天
  → 可行才加入
  → 更新当前位置和时间后继续选下一个
```

当前实现可能先选出空间上不合理的景点，最后再把超时景点截掉。这样能产生一个不越界的时间表，但不能证明选到的是剩余候选中更合适的可行景点。

### 5.4 P0：时间表是事后截断，不是选点约束

`ScheduleBuilder` 当前会寻找“已选景点列表的最长可行前缀”。如果第三个景点不合适，它不会尝试用更近、耗时更短的第四个候选替换，而是直接停止当天安排。

动态排程完成后，`ScheduleBuilder` 应从“负责裁剪选择结果”改为“负责生成和复核已经可行的时间线”。

### 5.5 P0：短行程的城市范围规则与报告不完全一致

开题报告将范围定义为“1～3 天单城市深度游，4～7 天同省多城市”。当前代码在 4～7 天会强制多城市，但 1～3 天只是默认建议单城市；用户明确选择时仍允许 2～3 个同省城市。

为了让产品边界、测试和论文一致，核心流程重组时应采用报告口径：

- 1～3 天只生成单城市方案；
- 4～7 天只生成同省 2～3 城市方案；
- 不再在 1～3 天流程中展示多城市选择；
- 对历史会话保留读取兼容，但新需求按新规则验证。

### 5.6 P1：普通模式没有路线和天气工具路由

开题报告要求普通模式按单一意图路由：

- 旅游知识 → Markdown RAG；
- 路线问题 → 高德 MCP；
- 天气问题 → 和风天气；
- 明确规划意图 → 提示切换规划模式。

当前普通模式主要完成知识 RAG、简单回复和规划意图拦截，没有独立的路线/天气查询意图模型、参数抽取和工具调用流程。

### 5.7 P1：普通知识库不含独立景点 Markdown

报告描述的是省份、城市和景点 Markdown 知识库。当前 `data/knowledge/` 只有省份和城市知识文档。景点知识主要来自 MySQL attractions，而不是独立的景点 Markdown 知识源。

这不是核心规划阻塞项。为避免重新开展大规模数据维护，建议普通模式需要景点知识时先检索 MySQL 景点描述，不在当前阶段另建全国景点 Markdown。

### 5.8 P1：Evaluator 与报告口径未完全一致

当前评估器没有直接把以下情况生成结构化 `EvaluationIssue`：

- 天气不可用或跳过；
- 路线使用估算或完全不可用；
- 路线数据缺失导致时间表不完整。

这些信息目前由 `DegradationNotice` 负责展示。工程上可以共存，但论文实验和统一指标需要明确：

- `EvaluationIssue` 表达方案质量和约束风险；
- `DegradationNotice` 表达外部数据可信度和服务降级。

另外，兴趣覆盖率目前通过景点名称、分类和描述中的关键词判断，没有直接基于景点标签，可能与硬筛选口径不一致。

### 5.9 P1：文档与代码存在冲突

当前说明文档和 README 中存在多处陈旧描述，例如：

- README 声称高德路线失败时不做 Haversine 估算，但代码会生成带 `estimated=true` 的估算路线；
- README 声称已有固定 A/B 实验集，但当前实验模块和运行脚本已删除；
- 健康接口固定返回 `Final M12`，不能反映开题报告最新版算法尚未闭环；
- 部分旧文档把现有流程描述为最终完成状态，容易影响后续开发判断。

文档同步应放在核心算法完成后一次性处理，避免边开发边反复改说明。

### 5.10 P0：当前 Git 工作区缺少安全基线

当前工作区约有：

- 102 个修改文件；
- 36 个删除文件；
- 64 个未跟踪文件。

这些改动包含架构调整、删除旧实验模块、新增普通模式、数据库脚本和数据质量工具。没有一个清晰基线时，后续很难判断动态排程修改导致了哪些回归。

此处只建议建立可回退点，不建议自动提交、自动丢弃或重置任何现有改动。

## 6. 目标核心架构

### 6.1 目标职责划分

| 模块 | 目标职责 | 是否使用 LLM |
| --- | --- | --- |
| Requirement Parser | 从自然语言形成结构化需求，本地规则补全与校验 | 是，可降级 |
| Destination Planner | 选择省份、城市和停留天数 | 否，确定性规则 |
| Candidate Retriever | 标签硬筛选、Chroma、BM25、PreferenceScore | 否 |
| Dynamic Scheduler | DistanceScore、Priority、时间窗口、候选循环 | 否 |
| Route Feasibility | 对优先候选查询真实路线并判断可行性 | 否，调用高德 |
| Weather Enrichment | 最终逐日天气补充 | 否，调用和风 |
| Evaluator | 规则检查和结构化问题 | 否 |
| Response Narrator | 将结构化结果转成自然语言说明，可选 | 可选 |

核心原则：LLM 可以解释，不能覆盖确定性算法的结果；LLM 不可用时，核心行程仍应生成。

### 6.2 建议的数据模型

新增内部候选模型，不直接污染数据库表：

```python
class PlanningCandidate:
    poi_id: str
    name: str
    city: str
    tags: list[str]
    longitude: float | None
    latitude: float | None
    visit_duration_minutes: int
    preference_score: float
    semantic_score: float | None
    keyword_score: float
```

每次动态决策生成内部轨迹：

```python
class CandidateDecision:
    poi_id: str
    day: int
    preference_score: float
    distance_m: float | None
    distance_score: float
    priority_score: float
    route_source: str
    feasible: bool
    rejected_reason: str | None
```

建议先把决策轨迹用于日志、测试和实验，不必第一版全部暴露给最终用户。最终方案至少保留被选景点的三个分数和路线来源，方便论文解释和问题排查。

### 6.3 动态排程算法

建议的确定性伪代码：

```text
输入：城市停留天数、候选景点、每日时间窗口、用餐和缓冲配置

unused = 所有通过标签硬筛选的候选

for 每一天:
    current_time = 每日开始时间
    current_location = None

    while unused 非空:
        if current_location is None:
            第一站按 PreferenceScore 选择
        else:
            计算 current_location 到所有候选的 Haversine 距离
            Dmax = 当前候选最大距离
            DistanceScore = 1 - distance / Dmax
            Priority = 0.7 * PreferenceScore + 0.3 * DistanceScore

        按 Priority 从高到低尝试候选:
            先用访问时长 + 基础缓冲做本地粗筛
            第一站无需路线；其余候选调用高德 Route
            Route 失败且坐标可用时生成带标记的 Haversine 估算
            计算交通 + 游览 + 用餐 + 缓冲后的结束时间

            if 可在当天结束时间前完成:
                加入当天
                更新 current_location 和 current_time
                从 unused 移除
                break，重新计算剩余候选 Priority

        如果所有候选均不可行:
            结束当天

输出：逐日景点、已验证路线、时间线、未选原因、决策轨迹
```

### 6.4 第一站和缺失坐标的确定规则

开题报告没有明确“每天第一站从哪里出发”。第一版建议采用最简单、可复现的规则：

- 每天第一站只按 `PreferenceScore` 选择；
- 不假设用户酒店或车站位置；
- 第二站开始才使用当前位置计算 `DistanceScore`；
- 未来如新增住宿位置，再把酒店坐标作为每日起点。

缺失坐标处理：

- 有明确兴趣匹配但缺少坐标的景点仍可作为第一站候选；
- 缺坐标景点不能参与后续距离优先度和路线验证时，应降低优先级或跳过，并记录原因；
- 不允许用城市中心点冒充景点坐标。

### 6.5 调用量控制

动态排程会增加路线调用次数，必须控制成本和延迟：

- 检索阶段每城市先取 20～30 个候选，不把全国数据送入规划器；
- 本地时长粗筛先排除明显放不下的候选；
- 每一轮只对 Priority 前 3～5 名调用路线；
- 继续使用 Redis 路线缓存；
- 同一对景点和模式命中缓存时不重复请求；
- 记录每次计划的路线调用次数、缓存命中率和总耗时；
- 如果全部真实路线失败，允许带明确标记的估算结果继续，不得伪装成真实路线。

| 坐标仍有不准确数据 | DistanceScore 和路线错误 | 代表城市先验收；缺坐标降级而不是伪造 |
| PreferenceScore 被归一化方式影响 | 实验结论不稳定 | 固定公式、保存原始分数、用消融实验比较 |
| LLM 输出波动 | 需求解析不稳定 | 本地规则合并；核心调度完全确定性 |
| 外部天气预报窗口有限 | 远期计划无法获得天气 | 标记 unavailable，不影响主计划生成 |
| 文档继续超前于代码 | 答辩时描述与演示冲突 | 每个里程碑结束后按代码事实更新文档 |
| 测试依赖当前日期 | 随日期自动失败 | 所有日期测试注入 reference_date |
| 旧方案模型兼容 | 历史方案读取失败 | Pydantic 迁移兼容、算法版本字段、回归样本 |

## 12. 第一批具体开发任务

建议下一次直接从以下任务开始，不再继续数据库批处理：

## 13. 最终建议

当前项目最值得保留的是完整的工程外壳和可靠性能力，最需要重做的是城市内部景点选择与排程核心。下一步不应推倒重来，而应沿用现有对话、检索、路线、天气、任务和前端模块，只替换中间这一段：

```text
旧：候选 → LLM/轮询分天 → 路线 → 截断

新：候选与 PreferenceScore
      → 动态 DistanceScore/Priority
      → 路线与时间可行性
      → 确定性逐步选点
```

完成这一替换后，系统的核心流程、开题报告创新点、测试指标和论文实验才能真正对齐。数据库质量优化可以在核心闭环稳定后，以不改变算法接口的方式继续推进。
