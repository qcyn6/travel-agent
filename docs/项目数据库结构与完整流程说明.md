# 个性化旅游规划系统：数据库结构与完整流程说明

> 文档版本：2026-09-17  
> 说明依据：当前工作区代码、SQLAlchemy 模型、接口实现和现有项目文档。  
> 本文描述的是“现在项目实际怎么运行”，不是早期方案中已经被删除或尚未接入的功能。

## 1. 项目一句话概览

这是一个以自然语言为入口的个性化旅游规划系统：

1. 用户先选择“普通对话”或“旅行对话/规划流程”。
2. 普通对话只负责开放式问答，不创建旅行需求，也不生成行程。
3. 旅行对话通过多轮自然语言交流收集目的地、天数、兴趣偏好等条件，形成可确认的旅行摘要；用户不需要填写需求表单。
4. 用户确认后，系统按“目的地决策 → 景点召回 → 大模型生成城市日程 → 路线 → 天气 → 景点表游玩时长 → 日程排布 → 方案评估”的链路生成方案。
5. 生成过程通过持久化任务和 SSE 进度事件返回前端，最终方案以版本形式保存到 MySQL，历史会话可以重新打开。

当前项目的核心边界是：

- 目的地目录覆盖全国省级行政区和目录中的城市/地区。
- 规划支持单城市 1～3 天，以及同一省份内 2～3 个城市、总计 1～7 天的多城市规划；每个选中城市至少安排 1 天。
- 跨省多城市规划目前会被明确拦截。
- 景点主数据由本地 MySQL 维护；当前演示数据是本地批量生成的项目数据，不是请求时临时联网爬取。
- 普通对话和旅行规划在接口、数据库表、提示词和前端历史分类上是分开的。

## 2. 系统由哪些部分组成

```text
┌──────────────────────────────┐
│ Vue 前端                      │
│ 首页、模式入口、聊天、侧边栏、方案页 │
└──────────────┬───────────────┘
               │ HTTP / SSE
┌──────────────▼───────────────┐
│ FastAPI 后端                  │
│ 对话、需求、规划、检索、路线、天气 │
└───────┬──────────┬───────────┘
        │          │
        │          ├──────────────┐
        │          │              │
┌───────▼──────┐ ┌─▼────────────┐ ┌▼────────────────────────┐
│ MySQL        │ │ Chroma       │ │ 外部能力                 │
│ 主数据/会话/ │ │ 景点向量索引 │ │ DeepSeek、DashScope、     │
│ 任务/方案    │ │              │ │ 高德、和风天气            │
└───────┬──────┘ └──────────────┘ └──────────────┬─────────┘
        │                                        │
        └────────────── Redis 可选缓存/任务队列 ──┘
```

### 2.1 MySQL：唯一的业务主存储

MySQL 保存需要长期保留、需要关联查询、需要保证一致性的业务数据：

- 全国省份和城市目录；
- 景点主表中的基础资料、标签、描述、坐标和游玩时长；
- 规划对话及消息；
- 普通对话；
- 规划任务、任务进度事件；
- 已生成的旅行方案版本。

### 2.2 Chroma：景点描述的向量索引

Chroma 不属于 MySQL 表。它是持久化在 `data/chroma` 下的向量库，用于语义检索景点描述。景点的权威基础信息仍在 MySQL；如果标签或描述改变，需要重新构建 Chroma 索引。

当前向量集合名为 `attraction_knowledge`。向量元数据只保存检索所需的景点名称、城市、分类、标签、坐标、描述、内容哈希和索引范围等信息，不另外建立一张 MySQL 向量表。

### 2.3 Redis：可选加速层和可选任务队列

Redis 不是景点主数据库，也不是会话主数据库。当前用途是：

- 缓存高德 POI、路线和和风天气等有时效性的外部结果；
- 在开启生产配置时，使用 Redis Streams 承载规划任务；
- Redis 不可用时，缓存旁路，规划任务可退回进程内 worker。

### 2.4 外部服务

| 服务 | 当前作用 | 是否规划必需 |
|---|---|---|
| DeepSeek | 需求理解、普通/旅行对话回复、城市日程生成 | 对话和生成质量依赖；有本地降级逻辑 |
| DashScope `text-embedding-v3` | 景点描述向量化 | 向量检索可降级，但语义召回会变弱 |
| DashScope `qwen3-rerank` | 混合召回后的候选景点重排 | 不可用时保留 RRF 顺序 |
| 高德地图 MCP | 本地景点筛选完成后补充已选 POI 详情；再根据相邻景点位置推荐路线和交通方式 | 详情失败保留本地候选；路线或距离失败时标记为不可用，不伪造路线结果 |
| 和风天气 | 直接获取行程城市的逐日天气 | 日期未填、超出 10 天窗口或接口失败时跳过/降级 |

Tavily 已不在当前主链路中；当前景点知识不通过 Tavily 实时补全。

## 3. 当前 MySQL 表总览

当前 SQLAlchemy 模型定义了 10 张业务表，来源是 `backend/database/tables.py`。

| 表名 | 中文理解 | 所属模块 | 关键作用 |
|---|---|---|---|
| `provinces` | 省级行政区目录 | 目的地目录 | 全国省份名称、行政区编码、兴趣画像 |
| `cities` | 城市/地区目录 | 目的地目录 | 省市关系、城市编码和城市兴趣画像 |
| `attractions` | 景点主表 | 景点知识/规划 | 规划候选景点的名称、标签、描述、坐标和游玩时长 |
| `conversations` | 旅行规划会话表 | 旅行对话 | 保存规划型会话的需求草稿、状态和生命周期 |
| `general_conversations` | 普通对话会话表 | 普通对话 | 独立保存普通问答，不带规划字段 |
| `conversation_messages` | 旅行规划消息表 | 旅行对话 | 一条一条保存规划对话消息和顺序 |
| `planning_jobs` | 规划任务表 | 异步规划 | 保存生成方案的任务状态、租约、重试和进度 |
| `planning_events` | 规划事件表 | 异步规划/SSE | 追加保存进度事件，支持断线续传 |
| `travel_plans` | 旅行方案版本表 | 方案保存 | 保存每次成功生成的完整方案快照 |

### 3.1 关系总图

```text
provinces 1 ─────── N cities 1 ─────── N attractions

conversations 1 ── N conversation_messages
       │
       ├──────────── N planning_jobs 1 ─────── N planning_events
       │
       └──────────── N travel_plans

general_conversations       （独立表，不与 planning 表建立外键关系）
```

这张关系图体现了一个重要设计：普通对话没有 `conversation_id` 外键指向规划会话，也没有规划需求字段，因此普通问答不会因为代码误用而混入规划流程。

## 4. 每张表的字段和项目作用

以下字段类型以 MySQL 中 SQLAlchemy 的定义为准。`JSON` 字段存储结构化对象或数组；它们不是完全自由的文本，业务代码会按 Pydantic 模型解释和校验。

## 4.1 `provinces`：省级行政区表

### 表的含义

保存全国省、自治区、直辖市、特别行政区等省级目录入口。它是目的地解析的第一层索引，也保存省级兴趣画像，帮助用户只说“云南”“江南风光”等较宽泛条件时完成目的地推荐。

### 字段说明

| 字段 | 类型/约束 | 含义 | 项目中的作用 |
|---|---|---|---|
| `id` | `Integer`, 主键 | 省份内部数据库编号 | 作为 `cities.province_id` 的关联目标；只用于数据库关联，不直接展示给用户 |
| `name` | `String(32)`, 非空、唯一、索引 | 省级行政区标准名称 | 目的地解析、展示、需求中的省份规范化；例如把用户输入映射为标准名称 |
| `adcode` | `String(6)`, 非空、唯一 | 高德行政区编码 | 给高德、天气以及后续外部服务提供稳定的行政区标识；同时可避免同名地区歧义 |
| `tags` | `JSON`，默认空数组 | 省份兴趣标签数组 | 与用户 `interests` 做交集匹配，参与省份/城市候选排序；例如自然、人文、美食等 |
| `description` | `Text`，非空 | 省份概况和旅行语义描述 | 目的地推荐、普通对话中的目的地上下文、规划前的解释性回复 |

### 关系和生命周期

- `ProvinceRow.cities` 是一对多关系，一个省可以有多个城市。
- 启动时由 `backend/database/seed.py` 根据 `backend/database/catalog.py` 幂等补齐和更新。
- 省份标签和描述主要由 `backend/database/city_profiles.py`/目录数据维护。
- 删除省份时，当前模型没有在关系上声明级联删除；正常业务不应直接删除目录省份，而应通过目录更新维护。

---

## 4.2 `cities`：城市/地区表

### 表的含义

保存可以被用户直接选择或被系统推荐的城市、地级市、自治州等目的地入口。它既是景点的归属层，也是同省多城市规划和城市兴趣匹配的核心表。

### 字段说明

| 字段 | 类型/约束 | 含义 | 项目中的作用 |
|---|---|---|---|
| `id` | `Integer`, 主键 | 城市内部数据库编号 | 作为 `attractions.city_id` 的外键；不作为跨系统 POI 标识 |
| `province_id` | `Integer`, 外键 `provinces.id`，索引 | 城市所属省份 | 做省市一致性校验，阻止跨省城市组合；加载城市的省份画像 |
| `name` | `String(32)`, 非空、唯一、索引 | 城市标准名称 | 目的地识别、用户展示、景点查询和生成方案中的城市名称 |
| `adcode` | `String(6)`, 非空、唯一 | 城市高德行政区编码 | 高德 POI、路线、行政区查询及天气上下文的稳定编码 |
| `tags` | `JSON`，默认空数组 | 城市兴趣标签数组 | 与用户兴趣做交集，参与省份只给出时的城市推荐，也用于城市描述的个性化匹配 |
| `description` | `Text`，非空 | 城市旅行画像和主题描述 | 普通对话目的地上下文、旅行对话目的地说明、规划时的城市语义背景 |

### 关系和生命周期

- `CityRow.province` 是多对一关系，指向 `provinces`。
- `CityRow.attractions` 是一对多关系，景点通过 `city_id` 归属城市。
- 省份只有一个时，`DestinationPlanner` 根据城市 `tags` 和描述选择城市。
- 用户明确给出多个城市时，`DestinationResolver` 校验所有城市是否存在、是否属于同一省。
- 当前规划允许同省 2～3 城市；跨省组合在解析阶段被拒绝。

## 4.3 `attractions`：景点主表

### 表的含义

保存系统真正用于规划候选召回的景点主数据。景点的标签和描述与省份/城市使用同一套兴趣交集思路：先通过标签判断是否匹配用户兴趣，再用文本和向量检索理解语义。

### 字段说明

| 字段 | 类型/约束 | 含义 | 项目中的作用 |
|---|---|---|---|
| `id` | `Integer`, 主键 | 景点内部数据库编号 | MySQL 行标识；不用于外部路线或向量索引的稳定 ID |
| `poi_id` | `String(64)`, 非空、唯一、索引 | 景点的稳定 POI 编号 | 连接景点主表、向量文档、路线起终点和最终方案；这是景点跨模块传递的主标识 |
| `city_id` | `Integer`, 外键 `cities.id`，索引 | 景点所属城市 | 按城市过滤景点候选，确保一个城市的规划不会拿到另一个城市的景点 |
| `name` | `String(128)`, 非空、索引 | 景点展示名称 | 前端展示、大模型候选输入、用户最终看到的景点名称 |
| `category` | `String(255)`, 可空 | 景点类型或分类 | 参与 BM25 和向量索引；帮助模型区分自然景观、历史文化、博物馆、街区等 |
| `tags` | `JSON`，非空，默认空数组 | 景点兴趣标签数组 | 与用户兴趣做精确交集计分；也进入 BM25/向量索引文本；用于硬排序保证明确匹配优先 |
| `description` | `Text`，非空，默认空字符串 | 景点知识描述 | 景点知识是否准备完成的主要判断依据；进入 BM25、Embedding、Rerank 和城市规划模型上下文 |
| `longitude` | `Float`, 可空 | 经度 | 高德路线查询、景点距离计算、天气查询前置判断；为空时路线直接标记为不可用 |
| `latitude` | `Float`, 可空 | 纬度 | 与经度成对使用，作用同上 |
| `visit_duration_minutes` | `Integer`, 非空，默认 `90` | 景点游玩时长，单位分钟 | 日程总时长和景点开始/结束时间计算；来源只认景点表，不读取高德游玩时长 |

### 特别说明

1. 当前 `attractions` 没有图片字段。此前决定暂不增加景点图片，因此前端方案页目前只展示文字行程。
2. 当前也没有 `rating`、`address`、`tourism_level`、`source`、`knowledge_status`、`data_source`、`description_origin`、`duration_origin`、`quality_status`、`quality_flags`、`is_active`、`coordinate_source`、`parent_poi_id` 等字段；这些旧字段已经被迁移删除，避免把与当前规划无关的来源、质量、生命周期和父子关系混入主表。
3. 早期的 `attraction_knowledge` 独立知识表已经移除。现在景点描述直接放在 `attractions.description`，结构更简单，检索直接读取主表。
4. `description` 为空的记录不会成为正常向量检索候选；知识准备服务会把已有描述视为 ready。
5. `attractions` 的字段白名单固定为 `id`、`poi_id`、`city_id`、`name`、`category`、`tags`、`description`、`longitude`、`latitude`、`visit_duration_minutes`。未经过用户确认和迁移设计，不得向该表新增字段。

### 关系和生命周期

- `AttractionRow.city` 指向一个城市。
- `poi_id` 是景点表、向量库、路线和最终方案中最重要的关联键。
- `GET /api/v1/cities/{city}/attractions` 默认先读取本地 MySQL，再为本地结果补充高德详情并写回坐标等事实字段；MCP 失败时保留本地结果。传 `use_amap=false` 可强制本地读取；外部空标签/空描述不会覆盖本地内容。

## 4.4 旧版 `attraction_facts`（已删除）

> 2026-09-17 重构后，`attraction_facts` 已从 SQLAlchemy 模型和 MySQL 中删除。旧版字段说明仅作为迁移背景保留；当前游玩时长直接读取 `attractions`，环境和开放时间不再进入规划模型。

### 表的含义

保存排程和评估需要的结构化景点事实。它与景点主表分开，是因为“景点是谁”与“景点适合怎么排”是两类信息；未来事实可以独立刷新，不必改动景点主记录。

### 字段说明

| 字段 | 类型/约束 | 含义 | 项目中的作用 |
|---|---|---|---|
| `id` | `Integer`, 主键 | 事实记录内部编号 | MySQL 行标识 |
| `poi_id` | `String(64)`, 外键 `attractions.poi_id`，唯一、索引 | 对应的景点 POI 编号 | 把事实准确挂到景点；与主表的数字 `id` 不同，当前是按 `poi_id` 关联 |
| `estimated_visit_minutes` | `Integer`, 非空 | 预计游玩时长，单位分钟 | 日程总时长和景点开始/结束时间计算；当前由事实数据或分类兜底生成 |
| `duration_source` | `String(32)`，非空 | 时长来源标记 | 区分 `web_extracted` 与 `category_fallback`，让方案知道时长是事实还是分类估算 |
| `opening_hours` | `JSON`，默认空对象 | 结构化开放时间 | 检查景点是否在开放时间内，给日程安排和最终提醒使用 |
| `source_url` | `Text`，可空 | 事实来源链接 | 保留可追溯入口；当前 DB-only 演示流程不通过它实时抓取网页 |
| `confidence` | `String(16)`，默认 `unknown` | 事实可信度 | 输出事实质量和降级判断；可取 high/medium/low/unknown |
| `checked_at` | `DateTime`，数据库当前时间默认值 | 首次检查或建立时间 | 记录事实何时被检查 |
| `updated_at` | `DateTime`，当前时间默认值并在更新时刷新 | 最近更新时间 | 事实刷新和排查过期数据的时间依据 |

### `opening_hours` 的 JSON 结构

接口模型 `OpeningHours` 对该字段解释如下：

```json
{
  "status": "known",
  "periods": [
    {
      "weekdays": [1, 2, 3, 4, 5, 6, 7],
      "open_time": "09:00",
      "close_time": "18:00",
      "last_entry_time": "17:30"
    }
  ],
  "raw_text": "每日 09:00-18:00",
  "applicability_text": "节假日可能调整",
  "confidence": "medium",
  "source_url": null,
  "checked_at": null
}
```

字段规则：

- `status` 为 `known` 时，`periods` 至少有一段时间；未知时可以为空。
- `weekdays` 使用 1～7 表示周一到周日，并自动去重排序。
- 时间统一为 `HH:MM`。
- `last_entry_time` 用于比闭馆时间更严格的入场判断。
- 如果事实未知，方案不会假装精确，而是加入 `opening_hours_unknown` 提醒。

## 4.5 `conversations`：旅行规划会话表

### 表的含义

这是“旅行对话/规划模式”的会话主表。它保存一条规划会话当前收集到的需求草稿，并通过外键连接规划消息、规划任务和生成方案。

### 字段说明

| 字段 | 类型/约束 | 含义 | 项目中的作用 |
|---|---|---|---|
| `id` | `String(36)`, 主键 | UUID 会话 ID | 前端当前会话、接口路径、任务关联和历史记录的稳定标识 |
| `title` | `String(128)`, 默认“新的旅行计划” | 侧边栏显示标题 | 首条用户消息或已识别目的地到来后自动生成，例如“云南之旅” |
| `status` | `String(24)`, 索引，默认 `draft` | 规划会话状态 | 表示还在收集、已确认、正在规划或已完成；常见值为 `draft`、`confirmed`、`planning`、`completed` |
| `requirement_draft` | `JSON`，默认空对象 | 当前合并后的需求草稿 | 每轮旅行对话都更新它；确认前允许继续修改，确认后作为规划输入 |
| `requirement_confirmed` | `Boolean`，默认 `false` | 核心需求是否已确认 | 用户在对话中回复确认或点击聊天快捷回复后，后端决定是否允许创建方案任务 |
| `created_at` | `DateTime`，数据库当前时间 | 会话创建时间 | 历史分组和审计 |
| `updated_at` | `DateTime`，当前时间默认值/更新时刷新 | 会话最近变化时间 | 侧边栏排序、历史“几分钟前”显示 |

### `requirement_draft` 的 JSON 结构

它对应 `RequirementDraft`/`TravelRequirement`，当前字段是：

| JSON 字段 | 类型 | 含义 |
|---|---|---|
| `province` | `string \| null` | 省级目的地，可由城市反推 |
| `cities` | `string[]` | 城市列表；单城市时通常只有一个元素 |
| `city_preference_confirmed` | `boolean` | 省份级安排是否已经确认具体城市，或明确交给 AI 推荐 |
| `days` | `integer \| null` | 旅行天数，总范围为 1～7 天；单城市为 1～3 天，多城市为 1～7 天 |
| `interests` | `string[]` | 兴趣标签，如自然、历史文化、古城、美食、摄影 |
| `preference_text` | `string \| null` | 自由文本偏好，如“节奏轻松、不想太赶” |
| `travel_scope` | `single_city \| multi_city \| auto` | 单城市、同省多城市或自动判断；对话确认前 `auto` 表示尚未确定 |
| `start_date` | `YYYY-MM-DD \| null` | 出发日期；至少从明天开始，支持明天、后天、下周一等相对日期解析为绝对日期 |
| `daily_start_time` | `HH:MM \| null` | 每天景点游玩的开始时间；必须与结束时间在同一天内 |
| `daily_end_time` | `HH:MM \| null` | 每天景点游玩的结束时间；必须晚于开始时间，景点不会排到该时间之后 |
| `transport_mode` | `auto \| walking \| transit \| driving` | 系统内部的路线模式；规划对话不采集该字段，默认保持 `auto`，由高德地图工具按相邻景点位置自动推荐 |

规划需求达到 ready 的条件是：目的地、天数、兴趣或自由文本偏好、出发日期、每日开始和结束时间、城市安排方式全部明确；如果是省份级单城市安排，还必须确认具体城市或明确交给 AI 推荐；`transport_mode` 保持系统默认的 `auto` 即可。1～3天默认建议单城市，想游多个城市时建议增加到4天以上。每日时间默认建议为 08:00～21:00，用户也可以在对话中指定其他同一天内的时间窗口；景点之间的路线在景点确定后交给高德地图工具推荐，用户如何到达目的地不参与规划条件。只有 ready 后，用户才可以确认并开始生成方案。

### 关系和生命周期

- 一条规划会话有多条 `conversation_messages`、多个 `planning_jobs` 和多个 `travel_plans`。
- 删除会话时，消息、任务、事件、方案会通过级联删除一起清理。
- 该表没有 `mode` 列。物理表本身就是 planning 模式；API/UI 层的 `mode=planning` 只是接口模型和边界校验。

## 4.6 `general_conversations`：普通对话会话表

### 表的含义

这是普通模式的独立会话表。它只用于开放式聊天，不携带目的地规划草稿，不创建规划任务，也不生成 `travel_plans`。

### 字段说明

| 字段 | 类型/约束 | 含义 | 项目中的作用 |
|---|---|---|---|
| `id` | `String(36)`, 主键 | UUID 普通会话 ID | 前端普通对话页面和普通历史记录的稳定标识 |
| `title` | `String(128)`, 默认“新的对话” | 普通会话标题 | 首条用户消息后自动截取生成，用于侧边栏显示 |
| `status` | `String(24)`, 索引，默认 `active` | 普通会话状态 | 当前普通会话主要使用 `active` |
| `messages` | `JSON`，非空，默认空数组 | 普通问答消息数组 | 将普通模式的用户/助手消息整体保存在本表中，避免进入规划消息表 |
| `created_at` | `DateTime`，数据库当前时间 | 会话创建时间 | 历史时间分组和排序 |
| `updated_at` | `DateTime`，当前时间默认值/更新时刷新 | 最近对话时间 | 侧边栏按最近活动排序 |

### `messages` 的 JSON 结构

数据库中每条普通消息只保存稳定所需的两项：

```json
[
  {"role": "user", "content": "北京有什么值得聊的？"},
  {"role": "assistant", "content": "北京可以从历史、人文、美食等方向聊起。"}
]
```

`role` 当前是 `user` 或 `assistant`，`content` 是文本内容。普通对话接口返回给前端时，会在内存中补齐展示所需的序号和时间模型；这些展示字段不单独落在 JSON 中。

### 这个表为什么不能和规划表合并

- 普通模式没有 `requirement_draft`、`requirement_confirmed`、`planning_jobs` 等概念。
- 普通模式遇到“帮我规划一个 3 天游”这类意图时，只会提示用户切换到规划模式。
- 分表让普通对话不会意外触发需求解析、景点检索、路线、天气和方案保存。
- 侧边栏可以直接按表/模式区分“普通对话”和“旅行对话/旅游方案”。

---

## 4.7 `conversation_messages`：旅行规划消息表

### 表的含义

保存 `conversations` 中的旅行规划对话，一条消息对应一行。它与普通对话的 JSON 数组不同，适合规划会话按顺序追加、查询和流式回复完成后持久化。

### 字段说明

| 字段 | 类型/约束 | 含义 | 项目中的作用 |
|---|---|---|---|
| `id` | `Integer`, 主键 | 消息内部编号 | 数据库行标识 |
| `conversation_id` | `String(36)`, 外键 `conversations.id`，索引，删除级联 | 所属规划会话 | 把消息归入对应旅行需求 |
| `sequence_number` | `Integer`, 非空；与会话组成唯一约束 | 当前会话中的消息顺序 | 保证用户和助手消息按顺序重放；SSE 文本完成后按此顺序读取 |
| `role` | `String(16)`, 非空 | `user` 或 `assistant` | 区分用户输入和 AI 回复 |
| `content` | `Text`, 非空 | 消息文本 | 前端聊天气泡、需求摘要和历史会话内容 |
| `created_at` | `DateTime`，数据库当前时间 | 消息创建时间 | 历史时间显示和审计 |

### 并发安全

`(conversation_id, sequence_number)` 有唯一约束 `uq_conversation_message_sequence`。仓储层在分配下一序号时锁定会话行，避免多个请求同时追加导致顺序冲突或覆盖。

## 4.8 `planning_jobs`：规划任务表

### 表的含义

保存一次“从已确认需求生成旅游方案”的可恢复执行状态。会话是业务上下文，任务是一次执行尝试；同一会话可以因为重新规划、失败重试而拥有多个任务。

### 字段说明

| 字段 | 类型/约束 | 含义 | 项目中的作用 |
|---|---|---|---|
| `id` | `String(36)`, 主键 UUID | 规划任务 ID | 前端 SSE、Redis 队列、worker 和方案保存的关联标识 |
| `conversation_id` | `String(36)`, 外键 `conversations.id`，索引，删除级联 | 所属规划会话 | 任务读取需求和回写会话状态 |
| `status` | `String(24)`, 索引，默认 `queued` | 任务状态 | `queued` 排队、`running` 执行中、`completed` 完成、`failed` 失败、`cancelled` 取消、`waiting_for_choice` 等待目的地选择 |
| `requirement_json` | `JSON`，非空 | 本次任务使用的需求快照 | 防止用户后续改动会话草稿后，正在执行的任务输入发生漂移 |
| `current_step` | `String(128)`, 可空 | 当前流程步骤 ID | 前端或日志显示现在进行到目的地、检索、路线、天气等哪一步 |
| `progress_json` | `JSON`，默认空对象 | 最新进度快照 | 保存类似 `{step, label, status}` 的可读进度；事件表则保存完整历史 |
| `error` | `Text`, 可空 | 最后一次失败的可读原因 | 失败页面、日志和告警展示 |
| `retry_count` | `Integer`, 默认 0 | 已领取/重试次数 | 诊断重复失败，也支持 worker 接管逻辑 |
| `worker_id` | `String(64)`, 可空、索引 | 当前租约持有者 | 多进程 worker lease：标记哪个 worker 正在执行，防止过期 worker 覆盖新结果 |
| `created_at` | `DateTime`，数据库当前时间 | 任务创建时间 | 排队时长、历史任务排序 |
| `started_at` | `DateTime`, 可空 | 最近一次开始执行时间 | 运行耗时和卡住任务排查 |
| `heartbeat_at` | `DateTime`, 可空 | worker 最近心跳时间 | 判断租约是否过期、是否可以被其他 worker 接管 |
| `finished_at` | `DateTime`, 可空 | 任务结束时间 | 统计总耗时和终态审计 |

### 任务状态简化图

```text
queued ──> running ──> completed
              │
              ├──────> failed
              ├──────> cancelled
              └──────> waiting_for_choice
```

### worker lease 是什么

worker 领取任务时会写入 `worker_id` 和 `heartbeat_at`，相当于暂时租用这条任务。worker 定期更新心跳；如果它崩溃，心跳超时，其他 worker 可以接管。完成、失败、进度更新都会再次检查当前 worker 是否仍然拥有有效租约，所以旧 worker 即使恢复，也不能把过时结果写回数据库。

## 4.9 `planning_events`：规划事件表

### 表的含义

这是规划任务的追加式事件日志，用来把后端的生成进度可靠地传给前端，并支持浏览器断线后从某个位置继续读取。它不是最终方案表，也不是普通聊天消息表。

### 字段说明

| 字段 | 类型/约束 | 含义 | 项目中的作用 |
|---|---|---|---|
| `id` | `Integer`, 主键 | 事件数据库编号 | 数据库行标识 |
| `job_id` | `String(36)`, 外键 `planning_jobs.id`，索引，删除级联 | 所属规划任务 | 把进度事件归入一次任务执行 |
| `sequence_number` | `Integer`, 非空；与任务组成唯一约束 | 当前任务内的事件序号 | SSE 的 `after` 游标；保证断线重连按顺序补发 |
| `event_type` | `String(48)`, 非空 | 事件类型 | 如 `job_queued`、`job_started`、`planning_progress`、`destination_choice_required`、`plan_completed`、`planning_error` |
| `payload` | `JSON`，默认空对象 | 事件具体数据 | 包含步骤名、标签、百分比、错误、计划 ID 等事件内容 |
| `created_at` | `DateTime`，数据库当前时间 | 事件产生时间 | 进度审计、耗时分析和调试 |

### 事件示例

```json
{
  "event_type": "planning_progress",
  "sequence_number": 5,
  "payload": {
    "step": "route_enrichment",
    "label": "正在获取景点间路线",
    "status": "running"
  }
}
```

事件表使用 `uq_planning_event_sequence(job_id, sequence_number)` 防止同一任务序号重复。SSE 连接可以携带 `after` 和 `job_id`，后端先回放已提交事件，再继续轮询新事件。

## 4.10 `travel_plans`：旅行方案版本表

### 表的含义

保存已经生成成功的完整旅游方案。每次同一规划会话重新生成成功，都会创建一个新的版本，不覆盖旧方案，因此“返回调整”和历史回看有数据基础。

### 字段说明

| 字段 | 类型/约束 | 含义 | 项目中的作用 |
|---|---|---|---|
| `id` | `Integer`, 主键 | 方案内部编号 | 方案详情接口和前端路由使用 |
| `session_id` | `String(36)`, 外键 `conversations.id`，索引，删除级联 | 所属规划会话 | 虽然字段叫 session，实际关联的是规划 `conversations.id` |
| `version` | `Integer`, 非空；与会话组成唯一约束 | 该会话的方案版本号 | 同一会话下按 1、2、3… 保存方案，避免新方案覆盖旧方案 |
| `requirement_json` | `JSON`，非空 | 生成该版本时的需求快照 | 以后打开方案时仍能知道当时按什么需求生成 |
| `plan_json` | `JSON`，非空 | 完整 `TravelPlan` 快照 | 前端逐日行程、景点、路线、天气、排程、评估和提醒的主要数据来源 |
| `evaluation_json` | `JSON`, 可空 | 单独保存评估结果快照 | 方便列表/后台快速读取评估；`plan_json` 内通常也包含 `evaluation` |
| `created_at` | `DateTime`，数据库当前时间 | 方案生成时间 | 历史方案排序和版本展示 |

### 方案 JSON 的结构

`plan_json` 对应 `backend/models/travel_plan.py` 中的 `TravelPlan`，主要结构如下：

```json
{
  "province": "云南省",
  "city_stays": [
    {"city": "昆明市", "days": 3}
  ],
  "city_plans": [
    {
      "city": "昆明市",
      "days": [
        {
          "day": 1,
          "attractions": ["西山风景区", "滇池"],
          "description": "围绕自然风光安排轻松的一日游。"
        }
      ]
    }
  ],
  "itinerary": [],
  "partial_knowledge_cities": [],
  "evaluation": null,
  "notices": []
}
```

各部分作用：

| 子结构 | 作用 |
|---|---|
| `province` | 最终确定的省份 |
| `city_stays` | 城市和停留天数，是多城市方案的骨架，最多 3 个城市 |
| `city_plans` | 每个城市按城市天数拆分的景点选择和日主题 |
| `itinerary` | 最终按全局 Day 1、Day 2…展开的逐日执行计划 |
| `partial_knowledge_cities` | 景点知识不完整、只能部分规划的城市 |
| `evaluation` | 方案是否通过，以及偏好、排程、路线、天气问题 |
| `notices` | 路线、天气和排程降级等对用户可见的说明 |

### `itinerary` 内的逐日字段

每个 `TravelDay` 包含：

| 字段 | 含义 |
|---|---|
| `day` | 全局第几天 |
| `city` | 当天所在城市 |
| `city_adcode` | 城市行政区编码 |
| `city_day` | 在该城市的第几天 |
| `date` | 真实日期；未填写出发日期时为空 |
| `attractions` | 当天景点停靠点列表，至少一个 |
| `routes` | 景点之间的路线段列表 |
| `weather` | 当日天气结果；可能为空或是 skipped/unavailable |
| `schedule` | 当日总排程，包括游玩、路线、用餐和缓冲时间 |
| `description` | 当日行程叙述和安排理由 |

每个 `AttractionStop` 还携带 `poi_id`、名称、城市、分类、描述、经纬度、游玩时长、开始时间和结束时间。游玩时长来自 `attractions.visit_duration_minutes`，前端显示为“游玩时长”，不显示参考来源。

## 5. 数据表之间怎样串起来

### 5.1 从省份到景点

```text
用户输入“云南/昆明/自然风光”
        │
        ▼
provinces.name/adcode/tags/description
        │  province_id
        ▼
cities.name/adcode/tags/description
        │  city_id
        ▼
attractions.poi_id/name/category/tags/description/坐标
        │  poi_id
        ▼
attractions.visit_duration_minutes
```

这里有三套不同粒度的标签：

- 省份标签：用于从较宽的省级范围中理解旅行方向；
- 城市标签：用于在省内选择更合适的城市；
- 景点标签：用于在确定城市后筛选具体景点。

它们不是三套互相独立的业务逻辑，而是同一套“用户兴趣与候选 `tags` 求交集”的逐级筛选。

### 5.2 从对话到方案

```text
conversations
   │ requirement_draft
   ├── conversation_messages    记录对话过程
   ├── planning_jobs            记录某次生成执行
   │      └── planning_events   记录进度和 SSE 回放
   └── travel_plans              记录成功方案版本
```

同一条会话中的“聊天内容”和“最终方案”是两类数据：

- 聊天内容保存在 `conversation_messages`，回答“用户是怎么提出需求的”；
- 当前需求保存在 `conversations.requirement_draft`，回答“现在要按什么条件规划”；
- 每次方案输入快照保存在 `travel_plans.requirement_json`，回答“这一版本当时按什么条件生成”；
- 最终结果保存在 `travel_plans.plan_json`，回答“生成了什么方案”。

这样，用户修改需求、重新规划时，旧版本仍然可以保留。

## 6. 从启动到最终方案的完整流程

## 6.1 后端启动流程

1. 后端读取 `.env` 中的 `DATABASE_URL`。
2. `get_engine()` 创建 SQLAlchemy MySQL engine，开启连接预检查和连接回收。
3. 应用生命周期调用 `init_database()`：
   - 导入全部 SQLAlchemy 表模型；
   - 执行 `Base.metadata.create_all(engine)`，缺表时创建；
   - 执行当前项目的 schema upgrade/migration，补索引、迁移旧字段并清理旧表结构。
4. 调用 `seed_catalog(session)` 幂等初始化省份和城市目录：
   - 不重复插入已存在的省市；
   - 更新目录中的标签和描述；
   - 不在每次启动时自动填充全部景点。
5. Redis、Chroma、外部 API 客户端按实际功能配置使用：
   - Redis 是可选连接；
   - Chroma 在向量检索/索引时使用；
   - 高德、天气、模型服务在相应流程中调用。

因此，后端启动会自动建/升级 MySQL 结构并补省市目录，但不会因为启动就重新抓取全国景点，也不会把所有外部 API 结果永久写进主库。

## 6.2 前端进入系统和历史恢复

1. 首页展示“普通对话”和“旅行规划”的入口。
2. 前端 store 根据当前模式，在浏览器 `sessionStorage` 中保存对应会话 ID。
3. 打开普通模式时，创建或恢复 `general_conversations` 会话。
4. 打开规划模式时，创建或恢复 `conversations` 会话。
5. 侧边栏分别加载三类历史：普通对话、旅行对话、旅游方案；点击时进入不同页面或恢复不同数据。

前端模式不是简单改变一段提示词，而是选择不同的 API 资源和数据库表。

## 6.3 普通模式流程

```text
创建普通会话
   ↓
POST /api/v1/general-conversations
   ↓
用户输入普通问题
   ↓
POST /api/v1/general-conversations/{id}/messages
   ↓
GeneralConversationService
   ├─ 保存 user 消息到 general_conversations.messages
   ├─ 判断是否包含“请规划/安排/去玩”等规划意图
   ├─ 若是规划意图：只提示切换规划模式
   └─ 否则：普通问答/目的地背景回复
   ↓
保存 assistant 消息到同一 JSON 数组
```

当前普通模式的边界：

- 可以聊目的地、风景、人文、美食、旅行灵感和一般问题；
- 可以提供省份/城市的背景介绍；
- 不合并旅行需求字段；
- 不访问规划消息表；
- 不创建 `planning_jobs`；
- 不调用景点检索、路线、天气和评估链路；
- 不生成并保存 `travel_plans`。

## 6.4 旅行对话收集需求流程

```text
创建规划会话 conversations
   ↓
用户自然语言输入
   ↓
POST /api/v1/conversations/{id}/messages
   ↓
保存 user 到 conversation_messages
   ↓
RequirementParser/DeepSeek 解析
   ↓
合并到 requirement_draft
   ↓
DestinationResolver 标准化省份、城市、别名和 adcode
   ↓
判断缺少哪些条件
   ↓
生成 assistant 回复并保存
   ↓
SSE 返回 requirement_updated、suggestions、message_delta、message_done
```

旅行需求的完整闭环条件：

- 目的地：省份或城市；
- 旅行天数；
- 兴趣标签或自由文本偏好；
- 出发日期；
- 每日景点游玩的开始和结束时间；
- 城市安排方式：单城市或同省多城市。

以上字段全部明确后才能生成方案。对话中的 `auto` 只表示该字段尚未确定，不能作为确认值；相对日期会转成当前日期基准下的绝对日期，并在回复里补充完整日期，避免“明天”失去上下文。

## 6.5 需求总结和确认流程

当需求从不完整变成 ready，或用户修改了核心字段时，旅行对话会主动给出总结，例如：

```text
目的地：昆明市
旅行天数：3 天
兴趣偏好：自然风光、摄影
城市安排：单城市深度游
出发日期：2026年9月20日（周日）
每日游玩时间：08:00—21:00
```

用户可以：

- 直接确认并生成方案；
- 继续补充/修改，更新 `requirement_draft`；
- 通过接口编辑需求，再重新确认。

确认接口会检查上述全部字段是否齐全，然后：

1. 设置 `requirement_confirmed=true`；
2. 把会话状态设为 `confirmed`；
3. 创建或复用一个 `planning_jobs` 任务。

## 6.6 规划任务创建和进度传输

```text
确认需求
   ↓
prepare_conversation 锁住会话
   ├─ 如果已有 queued/running 任务：复用，避免重复生成
   └─ 否则创建 planning_jobs(status=queued)
   ↓
写入 job_queued 事件
   ↓
dispatch_job
   ├─ Redis Streams 开启：进入外部任务队列
   ├─ Redis 不可用：回退进程内 worker
   └─ 开发默认：进程内任务注册表/worker
   ↓
worker 领取任务，写 worker_id/heartbeat_at
   ↓
规划过程中持续写 planning_events
   ↓
前端 GET /{conversation_id}/plan/events 使用 SSE 接收/回放
```

任务执行时，`planning_jobs` 保存“当前状态”，`planning_events` 保存“所有进度变化”。这就是为什么刷新页面或 SSE 断线后仍然可以继续显示，而不必依赖内存中的进度。

## 6.7 目的地决策流程

`DestinationResolver` 负责合法性，`DestinationPlanner` 负责选择性：

1. 识别省份、城市和别名，转换为标准目录名称。
2. 检查城市是否存在。
3. 检查多个城市是否属于同一省份。
4. 若给了明确城市：按单城市或同省多城市处理。
5. 若只给省份：使用省份/城市兴趣标签选择候选城市。
6. 单城市只接受 1～3 天；同省多城市只接受 1～7 天，并按城市数量校验最低天数：2 个城市至少 2 天，3 个城市至少 3 天。
7. `travel_scope=auto` 时，1～3 天默认单城市，4～7 天默认同省多城市，不再生成单/多城市二选一流程。

## 6.8 景点检索和城市日程生成

对每一个城市停留段执行：

1. 从 `attractions` 加载该城市且 `description` 非空的景点文档。
2. 先按标签与用户兴趣求交集；明确提供兴趣但没有标签命中的景点直接排除。
3. 只把自由文本偏好扩展为检索 query。
4. BM25 只对景点 `description` 做关键词检索。
5. Chroma 在本地景点向量中做语义检索，并按城市过滤；当前向量内容为 `name + category + tags + description`。
6. 使用 `0.7 × 语义相似度 + 0.3 × 关键词得分`计算偏好分，再按标签命中数和数据库顺序稳定排序。
7. 截取前 10 个本地候选交给 DeepSeek 城市规划器。
8. 城市行程生成后，仅对这批已筛选候选调用高德 `maps_text_search` 和 `maps_search_detail` 补充真实详情；高德不返回新的规划候选。
9. 高德详情成功时只写回分类、坐标等事实字段；标签、描述和游玩时长仍以本地数据库为准。
10. DeepSeek 返回结构化 `CityPlan`；若模型失败，使用确定性的候选轮转/兜底安排。

候选结果中的排名字段含义如下：

| 字段 | 含义 |
|---|---|
| `bm25_rank` | 关键词检索排名 |
| `interest_rank` | 标签交集兴趣排名 |
| `vector_rank` | 向量语义排名 |
| `rrf_score` | 多路结果融合分数 |
| `final_rank` | 重排和硬规则后的最终排名 |

## 6.9 生成全局逐日行程

城市级 `CityPlan` 只有“某城市第几天去哪几个景点”；系统随后把它展开为全局 `TravelDay`：

1. 把景点名称映射回 `poi_id` 和完整景点文档。
2. 按城市停留顺序计算全局 Day 1、Day 2……。
3. 写入城市 adcode、城市日序号和可选真实日期。
4. 为每个景点补充坐标、描述、类别和景点表中的游玩时长。

这样既保留了城市级规划结构，也能在方案页面中显示连续的全局行程。

## 6.10 路线增强

对同一天相邻景点调用路线服务：

1. 景点确定后，所有相邻景点路线默认使用 `auto` 模式，不向用户询问或读取景点间交通偏好。
2. `auto` 模式先调用高德 MCP `maps_distance`，按返回距离选择步行或公共交通等模式。
3. 首选高德 MCP 的步行、公交或驾车路线工具。
4. 命中 Redis MCP/路线缓存时直接读取。
5. 高德 MCP 路线或距离失败时，该路线段标记为不可用，不伪造路线结果。
6. 没有坐标时标记 `source=unavailable`。
7. 最终把路线放入 `TravelDay.routes`，并在需要时加入 `route_unavailable` 提示。

高德路线不是目的地规划的必经入口，但在方案已经确定景点以后，是“把景点串成可执行日程”的重要增强步骤。

## 6.11 天气增强

只有满足以下条件才查询逐日天气：

- 用户填了出发日期；
- 日期处于当前允许的查询窗口内（按明天到未来约 9 天判断）；
- 当天至少有一个景点且有坐标。

直接调用和风天气 API。结果写入 `TravelDay.weather`；如果没有日期、超出窗口、服务失败或数据不足，系统会记录 `skipped`/`unavailable` 状态和相应提示，而不是把未知天气伪装成确定天气。

## 6.12 景点表时长、排程和评估

### 景点规划字段

从 `attractions` 读取 `visit_duration_minutes`。高德 MCP 不提供也不覆盖景点游玩时长；高德返回的 `duration_min` 只表示相邻景点之间的交通时间。开放时间不参与模型、排程和评估。

### 日程排布

`ScheduleBuilder` 默认考虑：

- 每天规划时间窗口默认为 08:00～21:00，也可由用户指定同一天内的开始和结束时间；任何景点都不得跨出该窗口；
- 景点预计游玩时长；
- 景点之间路线时间；
- 约 40 分钟用餐时间；
- 每两个相邻景点之间固定 20 分钟缓冲，最后一个景点结束后不再追加；
- 每个景点的开始和结束时间。

结果写入 `TravelDay.schedule` 和景点的 `start_time`/`end_time`。状态可以是 `complete`、`estimated` 或 `incomplete`。

### 方案评估

`Evaluator` 检查：

- 兴趣覆盖是否足够；
- 每日总时长是否过密；
- 路线是否不可用或估算过多；
- 雨天户外安排是否过重；
- 景点表游玩时长和路线时间组合后是否过密。

问题会写入 `evaluation.issues`，每条问题包含类型、严重程度、涉及天数、原因和建议。

## 6.13 方案评估

规划完成后只进行一次确定性的可执行性检查：

1. 评估器产出 `EvaluationResult`。
2. 检查每日时间密度、景点间路线、天气和兴趣覆盖情况。
3. 发现问题时，将原因、严重程度、涉及日期和建议写入 `evaluation.issues`。
4. 保留原始规划结果，把问题展示给用户确认，不再调用第二次大模型，也不自动删减或替换景点。

## 6.14 保存方案和前端展示

规划成功后，应用服务在同一业务收尾阶段：

1. 把完整需求写入 `travel_plans.requirement_json`。
2. 把完整 `TravelPlan` 写入 `travel_plans.plan_json`。
3. 把评估结果单独写入 `evaluation_json`。
4. 计算当前会话的下一个 `version`。
5. 更新 `planning_jobs.status=completed` 和 `finished_at`。
6. 更新 `conversations.status=completed`。
7. 写入 `plan_completed` 事件。

前端收到完成事件后跳转方案页，从保存的方案快照展示逐日行程、路线、天气、方案检查、出行提醒和降级说明。聊天消息仍然保留在 `conversation_messages`，所以生成方案不会让旅行对话消失。

## 7. 检索链路的详细串联

```text
MySQL attractions
  ├─ city 过滤
  ├─ description 非空过滤
  └─ tags 兴趣交集排序
          │
          ▼
AttractionDocument
  name + category + interest_tags + description
          │
    ┌─────┼───────────────┐
    ▼     ▼               ▼
  BM25  Interest        Chroma Vector
    └─────┼───────────────┘
          ▼
      RRF 融合
          ▼
  DashScope qwen3-rerank
          │ 失败则保留 RRF
          ▼
   标签硬优先修正
          ▼
    CityPlanningService
          ▼
       DeepSeek
          ▼
      CityPlan
```

### 为什么不是把全国所有景点都发给大模型

系统先按城市过滤，再把 BM25、标签、向量和重排限制在有限候选中，最后只把候选景点的名称和描述交给城市规划器。这样可以：

- 减少模型上下文长度和调用成本；
- 降低模型从无关景点中选择的概率；
- 让兴趣标签成为可解释的第一层约束；
- 让向量库只承担语义召回，不取代 MySQL 主数据。

## 9. 外部服务失败时怎样处理

| 能力 | 正常情况 | 失败/缺失时的降级 | 方案中的体现 |
|---|---|---|---|
| DeepSeek 对话 | 生成自然语言回复 | 使用本地规则/模板回复 | 对话仍可继续 |
| DeepSeek 城市规划 | 返回结构化 CityPlan | 确定性候选轮转 | 仍可生成基础日程 |
| Embedding/Chroma | 语义召回 | 保留 BM25/标签候选 | 检索结果可能不够语义化 |
| `qwen3-rerank` | 对融合候选重排 | 保留 RRF 顺序 | 不阻断规划 |
| 高德 MCP 路线 | 获得真实步行/公交/驾车路线时长与距离 | MCP 不可用时标记为不可用，不使用旧版 API 或 Haversine 估算 | `route_unavailable` |
| 高德 MCP 距离 | 为 `auto` 模式提供距离判断 | MCP 不可用时该路线段标记为不可用 | `route_unavailable` |
| 和风天气 API | 获得城市未来逐日天气 | 跳过或标记不可用 | `weather_skipped` / `weather_unavailable` |
| 景点表规划字段 | 提供游玩时长 | 缺少记录时使用景点表默认值 | `schedule_incomplete` |
| Redis 缓存 | 读取/写入缓存 | 旁路缓存，直接调用/执行 | 不影响 MySQL 主流程 |
| Redis Streams | 外部 worker 消费任务 | 进程内 worker | 任务仍可执行 |
| 部分景点知识 | 城市候选足够 | 允许部分知识继续规划 | `knowledge_partial` |

设计原则是“可解释降级”：系统不把估算值伪装成真实值，而是把缺失或估算明确写入方案的 `notices` 和相关状态字段。

## 12. 日常维护时应该记住的规则

1. 改省份或城市目录：维护 `catalog.py`/画像数据，重启后由 seed 幂等补齐。
2. 改景点标签或描述：先写 MySQL，再运行向量索引重建脚本，否则 Chroma 仍是旧内容。
3. 改景点坐标：重新规划前确认路线缓存是否需要失效。
4. 改游玩时长：更新 `attractions.visit_duration_minutes`，然后重新生成方案才能看到新排程。
5. 不要把普通消息写进 `conversation_messages`；普通消息应该写 `general_conversations.messages`。
6. 不要把规划需求写进 `general_conversations`；普通模式没有需求收集流程。
7. 不要直接把 Redis 当主库；Redis 清空后，MySQL、Chroma 重建和外部调用仍应能恢复业务。
8. 删除规划会话会级联删除该会话的消息、任务、事件和方案版本；执行前要确认这确实是用户想删除的会话。
9. 删除或批量修改景点后，检查 `poi_id` 唯一性、`city_id` 归属和坐标完整性。
10. 需要确认真实数据规模时，以 MySQL 查询结果为准，不要只看 README 中的开发状态数字。

## 13. 术语速查

| 术语 | 含义 |
|---|---|
| POI | Point of Interest，景点/地点；本项目用 `poi_id` 作为跨模块稳定标识 |
| adcode | 高德行政区编码，用于省市和外部地图/天气上下文 |
| BM25 | 关键词相关性检索算法 |
| Vector Search | 将景点描述和用户需求转成向量后做语义相似度检索 |
| RRF | Reciprocal Rank Fusion，把多路检索排名融合成一个顺序 |
| Rerank | 对已经召回的有限候选再次按用户需求排序；当前默认是 DashScope `qwen3-rerank` |
| SSE | Server-Sent Events，后端持续向浏览器推送规划进度 |
| Lease | worker 对任务的临时租约；心跳过期后任务可以被其他 worker 接管 |
| Cache-Aside | 先查缓存，未命中再查外部服务并回写缓存 |
| Degradation Notice | 外部服务或数据不完整时写入方案的可解释降级提示 |

## 14. 最终理解：一条请求到底经过了什么

以“帮我安排昆明 3 天，喜欢自然风光和摄影”为例：

```text
用户输入
  ↓
Vue 规划对话页
  ↓
规划 conversations + conversation_messages
  ↓
解析为 requirement_draft
  ↓
城市目录校验：昆明市属于云南省
  ↓
用户确认
  ↓
planning_jobs + planning_events
  ↓
按 cities 找昆明的 attractions
  ↓
tags 交集 + BM25 + Chroma + RRF + qwen3-rerank
  ↓
DeepSeek 生成城市日程
  ↓
根据 poi_id 读取 attractions 游玩时长
  ↓
高德 MCP 路线/距离/缓存
  ↓（路线失败时）
高德 MCP 失败 → 路线段标记为不可用
  ↓
和风天气 API（有合适日期时）
  ↓
排程：游玩 + 路线 + 用餐 + 缓冲
  ↓
评估并将问题交给用户确认
  ↓
travel_plans 保存版本快照
  ↓
前端方案页展示逐日行程和检查提醒
```

如果用户只是输入“昆明有什么好玩的”，则走另一条完全独立的链路：

```text
普通模式
  ↓
general_conversations.messages
  ↓
普通对话提示词/回复
  ↓
不进入 requirement_draft、planning_jobs、景点规划和 travel_plans
```

这就是当前项目“普通对话”和“旅行规划”在数据、提示词、接口和执行流程上的完整边界。
