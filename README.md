# 山海拾光｜AI 旅游助手

山海拾光是一个面向自由行场景的旅游问答与个性化行程规划系统。用户既可以询问路线、天气和旅行注意事项，也可以通过自然语言描述旅行需求，在确认目的地、时间和个人偏好后，获得按天组织的行程方案。

项目将大语言模型的理解与表达能力，与本地景点检索、地图查询和程序化排程结合，提供从“了解目的地”到“制定行程”的完整体验。

## 核心功能

| 功能 | 说明 |
| --- | --- |
| 旅游问答 | 解答目的地介绍、旅行准备、安全注意事项等问题 |
| 实时信息查询 | 根据问题查询路线、天气和附近地点，并展示相关信息卡片 |
| 需求对话 | 通过多轮对话收集、补充和修改旅行条件 |
| 个性化规划 | 结合城市、兴趣、距离、开放时间和每日时间窗口生成行程 |
| 方案展示 | 展示每日景点、时间安排、地图路线、酒店参考及可查询的天气 |
| 历史记录 | 保存独立会话和旅行方案，支持返回查看 |
| 管理后台 | 管理用户资料、对话和方案，维护景点资料及旅行指南 |

## 两种使用模式

### 普通模式：随时提问，按需查询

普通模式用于解决具体的旅游问题，例如：

- “杭州东站到西湖怎么走？”
- “西湖附近有哪些餐厅？”
- “去高原旅行需要准备什么？”

系统由一个 LangChain ReAct Agent 处理当前会话。Agent 根据问题决定直接回答、向用户追问，或调用工具查询，再整合信息生成答复。

| 工具 | 作用 |
| --- | --- |
| 路线查询 | 获取地点之间的路线、距离和预计耗时 |
| 天气查询 | 查询城市在指定日期的天气信息 |
| 附近地点搜索 | 查找明确地点周边的餐饮、停车场等设施 |
| 旅行指南检索 | 检索行前准备、安全及旅行注意事项等知识 |

每个会话分别保存消息和摘要，避免不同会话的上下文混用。工具设置独立超时及整轮处理预算，查询失败时提供明确提示。

### 规划模式：先确认需求，再生成行程

规划模式用于把用户的旅行想法整理成可查看的每日方案。

```text
自然语言描述需求
        ↓
Agent 收集与修改条件，后端校验合法性和完整性
        ↓
用户确认本次旅行需求
        ↓
解析目的地 → 筛选景点并排程 → 补充行程信息 → 检查与内容增强
        ↓
展示并保存旅行方案
```

需求包括目的地、旅行天数、兴趣、节奏偏好、出发日期和每日游玩时间。用户可以在对话中补充或修改条件；条件完整后，系统提供确认入口，只有用户确认后才启动正式规划。

正式规划由 LangGraph 编排四个子图：

| 阶段 | 主要工作 |
| --- | --- |
| 需求与目的地解析 | 整理已确认需求，确定城市及停留天数 |
| 城市排程 | 从本地景点资料中检索候选，结合偏好、距离和时间条件安排景点 |
| 行程补全 | 组装每日计划，补充酒店参考、路线、天气和时间表 |
| 质量检查与内容增强 | 检查路线耗时、时间窗口等问题，补充景点介绍和旅行建议 |

当前支持 **1～3 天单城旅行、4～7 天同省 2～3 城旅行，最多 3 城**。出发日期从明天起，每日游玩时间由用户明确提供。

## AI 在项目中负责什么？

项目没有让模型直接凭空生成全部行程，而是按任务划分职责：

| 参与部分 | 职责 |
| --- | --- |
| 普通问答 Agent | 理解问题，决定是否调用工具，并整合结果回答 |
| 规划对话 Agent | 理解旅行意图，通过工具查询目的地、更新需求草稿和提交确认检查 |
| 后端校验与排程程序 | 检查条件是否合法、检索景点、安排顺序与时间，并校验可行性 |
| 内容增强 Agent | 为已有行程补充介绍、概述和建议，不直接改写景点顺序及时间表 |
| LangGraph | 串联正式规划各阶段，管理执行状态 |

这种分工让自然语言交互保持灵活，同时让关键条件和行程安排接受程序检查。排程采用启发式方法，不是数学最优化求解器，也不承诺全局最优路线。

## 技术架构

项目采用前后端分离架构，页面交互、业务接口、模型调用、数据检索和后台任务分别承担明确职责。

| 层次 | 技术与用途 |
| --- | --- |
| 前端 | Vue 3、TypeScript、Pinia、Vite，负责聊天、行程和后台管理页面 |
| 后端 | Python、FastAPI、Pydantic，负责接口、参数校验和业务处理 |
| 数据库 | MySQL、同步 SQLAlchemy / PyMySQL，保存用户、景点、会话、任务及方案 |
| 智能体与工作流 | LangChain、LangGraph，分别处理工具调用与规划编排 |
| 景点检索 | 城市及兴趣筛选、BM25 关键词检索、Chroma 向量检索 |
| 后台任务 | Redis Streams 与独立 worker，执行正式规划任务 |
| 状态与进度 | MySQL 执行事件、SQLite 规划检查点、SSE 实时进度推送 |
| 外部服务 | 高德地图、和风天气及大模型与文本嵌入服务 |

旅行指南与景点候选使用不同的数据用途：**指南用于旅游知识问答，景点资料用于行程候选检索与排程**，不把普通指南文档直接当作景点加入路线。

## 用户与管理员

**普通用户**可以进行旅游问答、确认规划需求、生成行程，并查看自己的会话和方案。

**管理员**可以查看普通用户资料、对话和方案，维护景点资料和旅行指南，并执行对应的检索索引同步。

后端检查用户身份、角色及数据归属。普通模式的聊天内容不会自动作为正式规划条件；规划任务以用户确认的需求为准。

## 项目特点

- **问答与规划分离**：日常咨询不直接触发行程生成，正式规划保留明确的需求确认环节。
- **真实数据辅助决策**：结合本地景点资料与外部地图、天气查询，减少仅凭模型描述安排行程。
- **多种方式检索景点**：利用城市、兴趣标签、关键词和向量匹配寻找候选景点。
- **逐步安排与校验**：根据已选景点更新位置和时间，结合路线与开放信息判断后续安排。
- **生成过程可见**：通过实时事件展示规划进度，并保存任务、方案和可恢复状态。
- **知识资料可维护**：管理员可以维护旅行指南与景点资料，更新相关检索索引。

## 主要目录

```text
backend/       后端接口、会话 Agent、规划流程、检索及数据库操作
frontend/      用户页面、行程展示和管理后台

deploy/        部署相关配置
```

## 能力边界

项目用于辅助旅游咨询与行程决策，不提供酒店或门票预订。跨省规划、完整城际交通安排和预算最优化不属于当前能力承诺。

模型和外部数据可能出错：开放时间缺失不代表全天开放，远期天气可能无法查询，路线估算也不等于实时查询结果。用户仍需在出发前核实景点开放情况、交通和酒店信息。
